# 2026-06-04

- **Removed the earlier `OPL_FLOAT` and `OPL_SIMD` experimental forks and replaced them with one clean-room, DBOPL-architecture-inspired block-SIMD float fork behind `-DOPL_BLOCKSIMD`** (off by default; the integer build stays the faithful, bit-exact one). Deleted `OPL3FloatDSP.swift` + `OPL3SimdDSP.swift`; unwound all `#if OPL_FLOAT/OPL_SIMD` scaffolding back to the pure integer path (`OPLSample` is unconditionally `Int16` again, `mixbuff` `Int32`, the SoA mirror hooks gone). The two superseded forks are preserved in git history (commit `12e2523`) and summarised in `Performance.md` so their conclusions aren't lost.
- **New `OPL3BlockSimd.swift` (`#if OPL_BLOCKSIMD`).** A from-scratch block-generating SIMD float engine that `OPL3Chip.generate4Ch()` delegates to under the flag. It reads config straight from the AoS `slot`/`channel` register layer each block (no SoA mirror) and keeps its own float dynamic state. Pieces: **exact integer phase accumulator** (per-block increment, vibrato sampled per block); **state-dispatched float envelope** advanced by per-`rate` *average* increments (`OPL3EGRates`, derived by simulating Nuked's global EG clock once at startup) instead of the per-sample `OPL3_EnvelopeCalc` switch; **branchless polynomial sine** (parabola + one refinement, ≈0.07 %, no table gather) × a linear gain LUT, evaluated `SIMD8<Float>` over the block; **idle-operator culling** (released + silent operators skip envelope + synthesis); **scalar fallbacks** for feedback (two-sample recurrence) and rhythm (per-sample noise LFSR + bespoke phase bits). Operator full-scale kept at ±4084 (= integer `OPL3_EnvelopeCalcExp(0)`) so FM depth is unchanged.
- **LICENSE — clean-room, NOT DBOPL.** DOSBox's DBOPL (`dbopl.cpp`) is the canonical fast block OPL3 but is **GPL-2.0-or-later**; this package is **LGPL-2.1**. A port/transcription would be a derivative work (translation doesn't shed copyright) and would force the whole distributed work to GPL. Only DBOPL's *techniques* (state dispatch, block generation, per-block LFO) are reused — general architecture, not copyrightable expression. `dbopl.cpp` was never opened; the engine is written against the Nuked/LGPL math the package already uses. `References/` still holds only LGPL sources. Full analysis in `Performance.md`.
- **Performance (release, `oplbench`, Apple Silicon, best-of-3).** Pure chip DSP (single sustained note) **2.75 s → 1.25 s** (44× → 96×, **2.2× faster** — culling skips 34 of 36 idle operators the integer chip still runs). Full driver→chip→44.1k render of DUNE8 sub2 **1.34 s → 1.12 s** (45× → 53×, **~20 % faster** — the representative figure). The block fork beats the heavily-optimised integer chip by attacking the dominant EG/phase *control* cost (state dispatch + culling), not just the synthesis. `oplbench` self-labels `[block-simd-float32 DSP]`.
- **Accuracy (`OPL3GoldenTests.goldenTolerance`, `#if OPL_BLOCKSIMD`).** RMS vs the Nuked PCM goldens: **sine_note 0.127 %, resample 0.126 %** (tonal, peak ≈0.34 %) — on par with the simplest float synthesis despite the EG also being approximated. `fourop`/`waveforms` are silent in Nuked (vacuous). **Rhythm is reported but not asserted**: OPL rhythm percussion is a global noise LFSR consumed in strict slot-interleaved per-sample order, which block generation + culling necessarily reorder — the drums decorrelate from Nuked (still sound like percussion, just different). An inherent block-engine limitation, documented. Tests gated: bit-exact `golden` and the three exact integer-DSP unit tests (`clipSample`/`slotCalcFB`/`slotGenerate`) are now `#if !OPL_BLOCKSIMD`. Both builds green (68 default incl. bit-exact; 65 under the flag), zero warnings on a clean build in each.
- Fixed a latent bug found in review: `fillGain` was clobbering `op.pgReset` (set on the key-on edge in `fillBlock`) back to `false` before `synth` consumed it, dropping the phase-reset-on-key-on. `pgReset` is now owned by the key-sync edge and cleared in `synth`. (Output for the keyed-at-phase-0 golden was unchanged; the bug would have surfaced on re-keyed notes.)
- **Modelled rhythm percussion faithfully (block fork): rhythm golden 34 % → 1.025 % RMS, now asserted (≤2 %).** A naïve block port of the OPL rhythm unit is badly wrong; three per-sample state machines had to be reproduced, each of which a block-over-time loop reorders:
  1. **Noise LFSR.** Nuked advances a global 23-bit LFSR once per operator per sample (36×/sample, slot order); HH/SD read `noise & 1` after 13/16 advances. New `synthRhythm` advances it 36×/sample in a dedicated loop (only when rhythm mode is on — zero cost on melodic tracks) and snapshots the two read points. The melodic/feedback paths no longer touch noise. Because the LFSR value depends only on the advance *count*, the snapshots match Nuked bit-for-bit.
  2. **rmHH/rmTC bit coupling.** HH(13)/SD(16)/TC(17) are processed per-sample in slot order so the bit cross-references match (slot 13 sets the HH bits + reads last sample's TC bits; slot 17 sets the TC bits + reads this sample's HH bits). Replaces the earlier broken per-slot full-block loops.
  3. **Channel-sample-delay quirk (the big one: 22 % → 1 %).** Nuked computes the LEFT mix after only slots 0..14, so a channel output referencing a slot ≥15 reads the *previous* sample — and the rhythm channels 6/7/8 use slots 15/16/17. `mix` now resolves each channel-output ref with a "fresh-through" threshold (14 for left, 32 for right) and a `carryOut[36]` bridge across block edges, reproducing OPL3_Generate4Ch's 4-group split. (The tonal goldens use only channel 0 / slots 0,3, so they were unaffected throughout — which is exactly why this bug hid behind a passing tonal suite.)
  - Also modelled Nuked's **one-sample `eg_out` lag** (gain emitted from the pre-update attenuation, then the envelope advanced) — removes the per-note-onset transient (rhythm peak 25 % → 3 %), and fixed the EG `nonzero` gate (the average-rate table can't recover "register rate ≠ 0" from the combined `rate`, so register-rate==0 ⇒ frozen is now handled in `fillGain`). BD (12/15) and TT (14) carry no noise and stay on the vectorised block path.
  - **Perf after rhythm work (best-of-3):** chip 2.78 s → 1.43 s (44× → 84×, ~1.95×; down from 96× — the quirk-aware mix resolves each ref twice); render unchanged at 1.12 s (53×, ~20 %). The rhythm 36×/sample noise loop only runs under rhythm mode, so melodic tracks keep the full win. Full write-up: `Performance.md` §Rhythm.

## Superseded same-day forks (now removed — kept for the record)

- **Added an EXPERIMENTAL floating-point DSP fork behind `-DOPL_FLOAT` (off by default; the integer build stays the faithful, bit-exact one).** Goal: measure whether a 32-bit-float synthesis path is faster than the integer log-domain chip on Apple Silicon. Deliberately *not* a faithful transcription — see the warning header in `OPL3FloatDSP.swift`.
- Introduced `OPLSample` typealias (`Int16` default, `Float` under `OPL_FLOAT`) in `OPL3Types.swift:24`; forked `Slot.out/fbmod/prout` (OPL3Types.swift:47) and `OPL3Chip.mixbuff` (OPL3Chip.swift:54) to it, and changed `sample(at:)` to return `OPLSample` (OPL3Chip.swift:101). All *control* logic (envelope state machine, 23-bit phase accumulator, register decode, routing, LFOs, EG clock, timed write buffer) is **unchanged and shared** between the two builds.
- New `OPL3FloatDSP.swift` (`#if OPL_FLOAT`): float analogues of `OPL3_SlotGenerate`/`SlotCalcFB`/`ClipSample`/`Generate4Ch`. Synthesis is a real interpolated sine (1024-entry LUT, lerped) × a linear envelope gain (`gain[egOut] = 2^(-egOut/32) · fullScale`) instead of the log-sine ROM + exponential ROM; feedback `>>(9-fb)` → `×2^-(9-fb)`; the `accm & cha` pan trick → multiply by {0,1}. Operator full-scale kept at ±4084 (= integer `EnvelopeCalcExp(0)`) so the FM phase-modulation depth and amplitude scale match the integer chip. The integer counterparts are wrapped `#if !OPL_FLOAT` in `OPL3Phase.swift`/`OPL3Generate.swift`.
- **Accuracy (tolerance golden vs the existing Nuked PCM fixtures, `OPL3GoldenTests.goldenTolerance`, `#if OPL_FLOAT`):** RMS error vs the integer golden is **0.13%** (sine_note), **0.12%** (resample 44.1k), **1.0%** (rhythm — noise-driven percussion that clips to full scale); peak ≤2.35%. (`fourop_49716`/`waveforms_49716` goldens are silent in the Nuked reference itself, so those two cases are vacuous.) The idealized float DSP tracks the integer chip to ~0.1% on tonal content. The bit-exact `golden` test is now `#if !OPL_FLOAT`; the three exact integer-DSP unit tests in `OPL3PhaseTests` (clipSample/slotCalcFB/slotGenerate) are likewise gated.
- **Performance (release, `oplbench`, Apple Silicon; best-of-3):** pure chip DSP **6.90 s → 6.51 s** (43× → 46× real-time, **~6% faster**); full driver→chip→44.1k render of DUNE8 sub2 **2.65 s → 2.54 s** (45× → 47×, **~4% faster**). Modest, as expected: the floated waveform/exp/mix is only a slice of the per-operator cost — the envelope state machine and phase generator (pure integer control logic) dominate and are unchanged. `oplbench` now self-labels the DSP (`[int DSP]` / `[float32 DSP]`).
- **Applied the transferable "Training an LLM in Swift" matmul-article optimizations to the float path** (the only ones that fit: most of the article — multithreading, AMX, Metal — is N/A to a serial FM chain, and the chip's mutable state was already on unsafe buffers). Two changes, both in `OPL3FloatDSP.swift`:
  1. The float LUTs (`sine`/`gain`/`feedback`) moved from `[Float]` to owned `nonisolated(unsafe) static let UnsafeMutableBufferPointer<Float>` (process-lifetime constants), dropping the per-lookup Swift-array bounds check from the hot loop — the article's lesson #1 applied to the read-only tables. Indices are provably in range (`& 1023`, `min(egOut,1023)`, fb∈1…7).
  2. The sine lerp uses a fused multiply-add (`Float.addingProduct`, stdlib — no swift-numerics dependency) — the article's FMA lesson. It is the one genuine mul-add site; the rest of the DSP is single-mul or single-add, so FMA has little else to fuse here.
  - **Result (release, chip DSP, best-of-3):** plain `-O` float **6.51 s → 6.10 s** (46× → 49× RT); render **2.54 s → 2.40 s** (47× → 50×). This recovers nearly all of the global `-Ounchecked` win (5.96 s / 50×) *safely*, with bounds/overflow checks left on everywhere else. Measured `-Ounchecked` for reference: int 6.74 s (45×, bit-exact preserved — checksum unchanged), float 5.96 s (50×). Accuracy unchanged by FMA (RMS still 0.13% / 0.12% / 1.0%).
  - **Net float-vs-int picture:** the integer baseline is 6.90 s (43×). Stacking the applicable article lessons lifts the float advantage from ~6% to **~12% at plain `-O`** (and ~14% with `-Ounchecked`). Still bounded because the integer envelope/phase control logic — untouched, unfloatable — dominates the per-operator cost.
- Documented the flag in `Package.swift` (commented `.define("OPL_FLOAT")`; build with `-Xswiftc -DOPL_FLOAT`). **Verified both builds:** default `swift test` 68 tests green + bit-exact intact, zero warnings on clean build; `-DOPL_FLOAT` build + tests green (incl. tolerance, unchanged after FMA), zero warnings on clean build.

- **Added a second experimental fork, `OPL_SIMD` (OPL3SimdDSP.swift): a Struct-of-Arrays chip that processes melodic channels as SIMD lanes.** Answers "can we vectorise channels?" — **conclusively no, it is ~50% slower.** Kept off by default and mutually exclusive with OPL_FLOAT; the faithful AoS chip is untouched.
  - **Architecture.** The faithful AoS register/reset/routing layer stays the source of truth (runs at ~72 Hz, not per sample). A persistent SoA mirror (`OPL3SimdState`) holds per-sample hot-loop state: operators reindexed `op = (carrier ? 18 : 0) + channel` so each row (18 modulators 0..<18, 18 carriers 18..<36) is contiguous for SIMD loads. Config is synced AoS→SoA on register-write dirty (`simdDirty`); dynamic state is seeded from AoS once after reset (`simdNeedsSeed`); verified the register layer never reads per-sample dynamic state, so the split is sound. Hooks added in OPL3Chip.swift (`write`/`writeBuffered`/`reset` + the buffered-write drain set `simdDirty`).
  - **Findings about the workload (grep of WestwoodADL):** the driver is pure OPL2 — never sets `newm`/4-op (`0x104/0x105`) or the OPL3 high bank — so **4-op is never used by the music** (only the silent `fourop` fixture). Rhythm mode (`0xBD` bit 5) **is** used, and its noise-LFSR percussion is irreducibly serial.
  - **Stage A (scalar SoA), validated.** A faithful slot-order re-expression of the float fork on SoA storage (config sync + modulation/output-routing resolution to SoA indices + per-operator noise sequencing + the two-pass mix / channel-sample-delay quirk). Tolerance is **identical** to the float fork (0.126% / 0.999% / 0.124%), proving the re-layout is correct. But it already benchmarks **6.46 s (46×) vs the float fork's 6.10 s (49×)** — ~6% slower before any SIMD, from the config-sync, the `op→slot` indirection, and the channel-output gather.
  - **Stage B (branchless SIMD4 over channel-lanes), validated.** Melodic operators processed in SIMD4 chunks: branchless **integer** SIMD `simdEnvVec` (EG state machine) and `simdPhaseVec` (phase) — bit-exact to the scalar path, so tolerance is **unchanged** (0.126% / 0.999% / 0.124%); feedback + waveform synthesis stay scalar per lane (the waveform is an inherently per-lane LUT). Rhythm section (ch 6–8) stays scalar in slot order; the noise LFSR advances by exact per-operator count (`simdAdvanceNoise`). Preserves the slot grouping, two-pass mix and the quirk exactly.
  - **Result: SIMD is decisively slower — chip DSP 9.34 s (32×) vs scalar SoA 6.46 s (46×) and float fork 6.10 s (49×); render 3.41 s (35×) vs 2.40 s (50×).** Output bit-identical to the float fork (checksum 213203 / -1522579862). Why it loses: SIMD4 lanes are built from 4 scalar gathers per field (≈14 loads in the EG, ≈6 in phase) and stored back via scalar loops; only **3 of 4 lanes are active** (channels group in 3s); the branchless EG computes *all* state-transition paths every sample; and all this overhead is spent on the per-operator arithmetic, which the float experiment already showed is the *minority* of the loop — the dominant integer control logic doesn't speed up. NEON's lack of gather + the serial FM/rhythm structure make "channels as SIMD lanes" a net loss here.
  - **Verdict:** SoA/SIMD-across-channels is not worthwhile for this chip. Kept behind `-DOPL_SIMD` as a documented, validated negative result. Both `OPL_FLOAT` and `OPL_SIMD` builds: tests green (incl. tolerance), zero warnings on clean build; the default integer build is unchanged and bit-exact.

- **Compared against DOSBox's DBOPL (`dbopl.cpp`) and wrote up the whole performance investigation in `Documentation/Architecture/Performance.md`.** DBOPL is an optimised *approximation* (not bit-exact): it hoists per-sample branching out of the hot loop via state-dispatched function pointers (`volHandler`/`synthHandler`/`waveHandler`, swapped on state change) and C++ template-specialised **block** generators (`GenerateBlock2/3`, `BlockTemplate<…>`), and amortises the LFO per block. That is the only design that targets our real bottleneck (the branchy integer EG/phase control logic), but its speed comes from the same bit-exactness sacrifice as the float fork (smaller tables + per-block LFO), and it is **GPL-2.0+** — unusable as a transcription source in this LGPL-2.1 package (`References/` keeps only the LGPL Nuked-OPL3 + AdPlug). Documented as architectural reference only. The bit-exact-preserving slice (per-slot waveform dispatch + block generation with per-sample LFO) is noted as the one untried direction if more speed is ever wanted.
