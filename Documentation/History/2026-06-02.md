# 2026-06-02

- Removed the driver's per-tick heap allocation: `AdLibDriver.Channel.dataptrStack` is now a fixed tuple `(Int?, Int?, Int?, Int?)` instead of `[Int?]` (AdLibDriver.swift:44), so `Channel` is a trivial value type and `initChannel`'s `_channels[c] = Channel()` (called per note/program setup at the 72 Hz tick) no longer allocates a stack array — real-time-audio safe. Added `Channel.dataptrStackCount` + `dataptrAtStack`/`setDataptrAtStack` tuple accessors and updated the three use sites in `update_jumpToSubroutine`/`update_returnFromSubroutine` (AdLibDriver+Opcodes.swift:163,167,177,188).
- Made `AdLibDriver.sink` a strong reference instead of `weak` (AdLibDriver.swift:94): `writeOPL` — the choke point for every register write — no longer pays an atomic weak-side-table load per write. No retain cycle exists (ADLPlayer → driver → sink → chip; nothing points back).
- Verified non-regression: 68 tests green (incl. the AdPlug trace-equivalence and bit-exact PCM goldens), zero warnings on clean build in both default and `-DOPL_TRACE` configs. The `oplbench render` checksum is **identical** to the pre-change baseline (1434131890 for DUNE8 subsong 2), proving byte-for-byte identical output.
- Added an Instruments harness: a `driver` mode to `oplbench` (driver tick only, no chip DSP — isolates the driver heap path for the Allocations instrument) and `Scripts/record-traces.sh` (builds release, records the full mode × {Time Profiler, Allocations} matrix into the gitignored `Traces/`, with per-row durations since Allocations runs ~30-40x slower, plus a `--time-limit` safety net so an overrun stops cleanly instead of a SIGKILL'd/corrupt bundle).
- **Backed the driver's three hot mutated arrays with owned `UnsafeMutableBufferPointer`** (`_channels`, `_programQueue`, `_soundData`; AdLibDriver.swift), matching the chip's `slot`/`channel` model. Added `init`/`deinit` to own the buffers; `setSoundData` copies the parsed bytes into an owned buffer (re-alloc/free managed). Enabled by the earlier `dataptrStack` tuple change (made `Channel` trivial). **This is a CPU win, not an allocation win** — see the measurement note below.
- **Measured allocations exactly (libmalloc `malloc_logger` interpose; `Scripts/count-allocs.sh`) and corrected an earlier mis-diagnosis.** The driver tick loop **never allocated per-tick** — not even in the committed baseline. Total allocations are a constant ~780 regardless of run length (216 ticks vs 144 000 ticks → same count); all are one-time startup/load. The Time Profiler's `beginCOWMutation`/`swift_allocObject` frames were a uniqueness *check* on a uniquely-owned buffer (no copy) and startup allocations, not per-tick COW copies. The slow `driver` Allocations *instrument* run (hit the time-limit) was a VM-Tracker/instrument-overhead artifact on this macOS 26 beta, not app allocations. The `UnsafeMutableBufferPointer` conversion removed only ~5-8 *startup* allocations (the per-channel `dataptrStack` arrays). Its real, large benefit is **CPU**: driver-tick CPU dropped ~4.9× (3.95 s → 0.81 s for 14.4M ticks) by removing Swift `Array` bounds checks, dynamic exclusivity enforcement, COW-uniqueness checks and element copies — the symbols that dominated the Time Profiler. Output byte-identical (render checksum 1434131890), 68 tests green, zero warnings, max RSS unchanged (~6.5 MB).
